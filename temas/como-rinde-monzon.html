Cómo se rinde (Monzón)

Esta página no es un TDA: es la metodología del examen de la cátedra de Monzón. La mayoría de los puntos no se pierden por no saber el algoritmo, sino por no cumplir reglas de entrega (usar genéricos, no escribir precondiciones, no mandar las estrategias). Usala como checklist: leela el día antes y otra vez al terminar, antes de comprimir y enviar.

1. Qué tipo de examen es

Es un examen basado en un proyecto (project-based), no un cuestionario de opción múltiple ni un papel con teoría. Tenés varias horas (el integrador, por ejemplo, da 3 horas y 30 minutos) y entregás un proyecto Java que compila y corre.

Lo que se corrige es código fuente real más todo lo que lo acompaña:

  • El código que resuelve cada ejercicio (clases, TDAs, métodos).
  • Un set de prueba en el main que demuestra que funciona.
  • Las estrategias escritas de cada método (carpeta strategies).
  • Las precondiciones (y en integradores también postcondiciones e invariantes) escritas en la firma de cada método.
🎯 La idea No alcanza con que el algoritmo sea correcto: tenés que documentar el contrato de cada método y probarlo. El examen evalúa que pienses como quien diseña una estructura, no solo que sepas codear. Manejá el tiempo: dejá un rato al final solo para precondiciones, estrategias, el set de prueba y la entrega.

2. Prohibiciones (¡esto desaprueba!)

⛔ Suficiente para desaprobar El enunciado lo dice textual: «Solo podrá utilizar técnicas vistas en este curso. Está prohibido el uso de librerías y genéricos, incluyendo estructuras que vienen con la JRE. No respetar este punto es suficiente para desaprobar el examen.» No importa cuán bien resuelto esté el resto.

Concretamente, en el examen NO podés:

  • Usar genéricos: nada de List<Integer>, Stack<String>, Set<T>, ni declarar clases con <T>. Tus TDAs trabajan con tipos concretos (típicamente int; el integrador deja elegir int o String).
  • Usar estructuras de datos de la JRE: nada de ArrayList, LinkedList, HashMap, HashSet, java.util.Stack, TreeMap, etc.
  • Importar librerías externas ni técnicas que no se vieron en clase.

Lo que sí podés usar: arreglos crudos (int[]), nodos enlazados que vos mismo definís, y los TDAs de la cursada que implementás a mano (Stack, Queue, Set, Dictionary, BinaryTree, Graph, …), en versión estática (arreglo) o dinámica (nodos).

// ❌ PROHIBIDO en el examen (genéricos + estructura de la JRE):
import java.util.ArrayList;
ArrayList<Integer> lista = new ArrayList<>();

// ✅ PERMITIDO: arreglo crudo de tipo concreto...
int[] datos = new int[100];
int cantidad = 0;

// ...o un TDA propio implementado a mano, sin genéricos:
Set s = new StaticSet();   // tu propia clase, trabaja con int
s.add(7);
⚠️ La trampa del apunte El apunte y los ejemplos de Monzón usan genéricos (vas a ver Stack<T> y similares en el material). Eso es solo para explicar: el examen los prohíbe. No copies el estilo genérico del apunte en tu entrega. Cuando programes para el examen, escribí los TDAs con tipos concretos (int).

3. Entregables que dan puntos

Más allá del algoritmo, hay entregables obligatorios. Faltar a varios de ellos puede desaprobar; cumplirlos es puntaje casi gratis. Checklist:

✅ Precondiciones en cada firma En la firma de cada método tenés que escribir sus precondiciones. En los integradores se pide además postcondiciones y los invariantes de la estructura (qué debe cumplirse siempre para que la estructura sea válida). Se documentan con Javadoc arriba del método (ver sección 4).
✅ Carpeta strategies Por cada ejercicio y método que escribís, va la estrategia en palabras (cómo lo pensaste y resolviste) dentro de la carpeta strategies, en formato txt, MD o pdf. Cualquier otro formato no se corrige.
✅ Set de prueba en el main Tenés que demostrar que tu código funciona con un set de prueba. No se piden tests unitarios: alcanza con armar pruebas en el método main del proyecto (crear la estructura, ejecutar los métodos, imprimir/verificar resultados).
// Ejemplo de set de prueba en el main (NO test unitario, solo pruebas en main):
public static void main(String[] args) {
    Dictionary d = new StaticDictionary();
    d.add(1, 100);
    d.add(2, 200);

    System.out.println("getValue(1) = " + d.getValue(1));  // espero 100
    System.out.println("getValue(2) = " + d.getValue(2));  // espero 200

    d.remove(1, 100);
    // eliminar una clave inexistente NO debe romper:
    d.remove(99, 0);                                        // no pasa nada (correcto)
    System.out.println("Pruebas OK");
}
✅ Comprimir src y nombrar bien el archivo Comprimís la carpeta src (junto a los txt de estrategias). El nombre del comprimido depende del examen:
  • Final (individual): APELLIDO_NOMBRE (apellido y nombre, en ese orden).
  • Integrador (grupal): el número de grupo.
El propio enunciado avisa: «verificar que cumpla con todas, en particular con los nombres de carpetas.» Un nombre mal puesto es puntaje regalado.
✅ Entregar bien Según el examen, el comprimido se coloca en la unidad compartida de UADE Labs y se verifica con el docente que se pudo abrir, o se envía por mail (en el integrador, a la casilla del profesor). Confirmá que el archivo llegó y se puede descomprimir antes de irte: una entrega que no abre es como no entregar.

4. Plantilla de contrato (Javadoc) por método

Cada método se documenta con un contrato: qué exige para funcionar (precondición), qué garantiza al terminar (postcondición) y, para una estructura entera, qué propiedad se mantiene siempre (invariante). Una plantilla que sirve para casi todo:

/**
 * Recupera el valor asociado a la clave k.
 * Pre:  el diccionario está inicializado y k es una clave existente.
 * Post: devuelve el valor v tal que el par (k, v) está en el diccionario.
 *       El diccionario no se modifica.
 * Invariante (de la estructura): no hay claves repetidas.
 * Manejo de error: si k no existe -> lanza RuntimeException (es un caso inválido).
 */
public int getValue(int k) { ... }

La decisión clave: ¿qué hago si se viola la precondición?

Para cada método tenés que decidir y dejar escrito qué pasa cuando lo llaman mal. Hay tres respuestas posibles, y elegir la correcta es parte del diseño:

DecisiónCuándo convieneEjemplo
Lanzar RuntimeException Cuando la llamada es realmente inválida y seguir daría un resultado sin sentido. getValue(clave) de una clave que no está: no hay valor que devolver.
Devolver un centinela (-1, null, false) Cuando "no encontrado / no aplica" es un resultado esperable que el llamador puede chequear. Un buscarPosicion(x) que devuelve -1 si x no está.
No hacer nada (operación idempotente) Cuando el efecto pedido ya está logrado o la operación no tiene sentido sobre ese estado. remove(clave) de una clave inexistente: el objetivo era que no esté, y no está.
📌 El ejemplo canónico: eliminar vs recuperar Es la pregunta clásica. Eliminar una clave que no existe NO es un error: pediste que esa clave no esté, y efectivamente no está — la operación simplemente no hace nada. En cambio, recuperar una clave que no existe SÍ rompe el contrato: te pidieron un valor que no existe, no hay nada coherente para devolver, así que se lanza una excepción.

Mirá cómo aparece esto en el StaticDictionary real de la cátedra:

// remove: si la clave NO está, recorre todo y termina sin hacer nada. No es error.
public void remove(int k, int v) {
    for (int i = 0; i < count; i++) {
        if (keys[i] == k) {
            keys[i] = keys[count - 1];   // tapo el hueco con el último...
            values[i] = values[count - 1];
            count--;                     // ...y achico.
            return;
        }
    }
    // clave inexistente -> no hace nada (correcto)
}

// getValue: si la clave NO está, NO hay valor que devolver -> lanza excepción.
public int getValue(int k) {
    for (int i = 0; i < count; i++) {
        if (keys[i] == k) return values[i];
    }
    throw new RuntimeException("No se encontró la clave");
}
💡 Cómo elegir rápido Preguntate: «¿el estado que pide ya quedó logrado?» Si sí (eliminar algo que no estaba), no hagas nada. «¿Me piden devolver algo que no existe?» Si sí (recuperar lo ausente), lanzá excepción. «¿"no encontrado" es un resultado normal que el llamador va a chequear?» Entonces devolvé un centinela. Sea cual sea, escribilo en el Javadoc.

5. Umbrales de aprobación y alcance por examen

Cada tipo de examen tiene su nota mínima y su alcance de temas. Saber el alcance te dice qué priorizar al estudiar.

ExamenPara aprobarHasta qué tema entra
Parcial ~60 % Hasta árboles (pila, cola, listas, conjunto, diccionario, árboles).
Final regular 60 / 100 Todo el programa, incluidos grafos y AVL / Árbol B.
Final previo 80 / 140 (≈ 57 %) Todo el programa (grafos, AVL, Árbol B, etc.).
🧭 Cómo te ayuda el alcance Si vas a parcial, grafos y AVL/Árbol B NO entran: clavá pila, cola, conjunto, diccionario y árboles binarios/ABB. Si vas a final, sí o sí sumá grafos y los árboles balanceados (AVL / Árbol B), que es donde están los ejercicios de más puntaje.
📊 Sobre la escala El integrador aclara que se mide con una escala logarítmica donde llegar a 60 puntos equivale a un 4 (aprobado). En todos los casos, además del puntaje, hay que cumplir TODAS las reglas de entrega de la sección 3: si fallás una, el examen queda desaprobado «sin excepción», tengas el puntaje que tengas.

6. El predicado por legajo

Muchos enunciados eligen la variante del ejercicio según tu legajo. El predicado es:

// En el final (individual): n = tu L.U. (legajo)
P(n) = (tu legajo) % 3      // da 0, 1 o 2 -> elegís el caso P que te toca

// En el integrador (grupal): se suman los legajos de TODO el grupo
P(a) = (suma de legajos del grupo) % 3 == 0
P(b) = (suma de legajos del grupo) % 3 == 1
P(c) = (suma de legajos del grupo) % 3 == 2

El enunciado lo plantea así: «Si el examen utiliza predicados, use la siguiente definición: P(n) = Su LU, módulo 3, es n.» En el integrador, en cambio, se basa en la suma de los legajos del grupo módulo 3 para repartir P(a), P(b) o P(c).

💡 Antes de arrancar Calculá tu P primero: legajo % 3 (o la suma del grupo % 3). Ese número te dice cuál de las variantes del ejercicio tenés que resolver. Resolver la variante equivocada no suma puntos, aunque esté impecable. Dejalo anotado para no confundirte a mitad del examen.

7. Resumen (checklist final)

  • Examen project-based: entregás código + estrategias + set de prueba, en varias horas.
  • Prohibido: genéricos y estructuras de la JRE. Solo técnicas de la cursada. (El apunte usa genéricos; el examen no.)
  • Precondiciones en cada firma; en integradores también postcondiciones e invariantes.
  • Carpeta strategies con la estrategia de cada método (txt/MD/pdf).
  • Set de prueba en el main (no tests unitarios).
  • Comprimir src; nombre APELLIDO_NOMBRE (final) o nº de grupo (integrador); entregar y verificar.
  • Para cada método, decidir el manejo de error: excepción / centinela / no hacer nada (eliminar inexistente = no error; recuperar inexistente = error).
  • Umbrales: parcial ~60 %; final regular 60/100; final previo 80/140. Parcial llega hasta árboles; grafos y AVL/Árbol B son de final.
  • Calculá tu predicado P = legajo % 3 (o suma del grupo % 3) para saber qué variante hacer.
